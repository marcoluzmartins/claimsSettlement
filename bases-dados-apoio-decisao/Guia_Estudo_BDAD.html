1 · Módulo 1Modelação Entidade–Relacionamento e modelo relacional

1.1 Ideias base

  • Dados = factos em bruto (42, 1850, 2026). Informação = dados com contexto/significado (Idade = 42). Informação útil: correta, atual, relevante, completa, acessível.
  • Base de dados = coleção organizada de dados relacionados, guardada de forma persistente (fechar a aplicação ou desligar o computador não apaga os dados).
  • SGBD/DBMS = software que permite criar, guardar, consultar, atualizar e gerir dados. Funções: armazenamento e acesso, integridade, controlo de acesso e segurança, concorrência, backup e recuperação. Exemplos: MySQL, PostgreSQL, Oracle, SQL Server, MariaDB, SQLite.
  • Níveis de abstração: físico (como os dados são guardados: ficheiros, índices), lógico (que dados e como se relacionam: tabelas, restrições), vista (o que cada utilizador/aplicação vê).
  • Do mundo real à BD: domínio/requisitos → modelo conceptual (ER) → modelo lógico (relacional) → implementação na BD.
  • Modelar dados = identificar e representar dados, relações e restrições do domínio: perceber o domínio, tornar relações explícitas, definir regras de negócio, reduzir ambiguidade antes de implementar.
  • No nível conceptual interessa o significado e estrutura dos dados, não tabelas, índices ou armazenamento.

1.2 O modelo Entidade–Relacionamento (ER)

Modelo conceptual com três blocos: entidades (coisas/conceitos de interesse: STUDENT), atributos (propriedades: Name, DateOfBirth) e relacionamentos (associações entre entidades: ENROLLED_IN).

Entidades

Procura no enunciado as “coisas” principais: pessoas, organizações, produtos, serviços, locais, documentos, eventos, transações. Nem todo o substantivo é uma entidade — tem de ser algo relevante para o sistema de informação. Pergunta de decisão atributo ou entidade? “Este conceito precisa de existir independentemente no modelo?” (partilhado por vários, com propriedades próprias → entidade; senão → atributo).

Identificadores e chaves

  • Identificador: atributo (ou combinação) que identifica unicamente cada instância. Toda a entidade deve ter um. Idealmente baseado em informação que não muda com o tempo.
  • Chave candidata: atributo(s) único(s) e mínimo(s) (retirar qualquer atributo destrói a unicidade). Chave primária (PK): a candidata escolhida para identificar as instâncias. Ex.: STUDENT(StudentID, Name, Email) — StudentID e Email (se único) são candidatas; escolheu-se StudentID.
  • Identificador composto: dois ou mais atributos. Típico em entidades associativas: ENROLLMENT(StudentID, CourseID, EnrollmentDate) — nenhum sozinho identifica; o par sim, e é mínimo.

1.3 Relacionamentos

Ligação lógica entre entidades. Quatro características a identificar em cada um:

Notação (mín, máx) — a leitura que usamos

O par (min,max) escreve-se junto da entidade e diz em quantas instâncias do relacionamento cada instância dessa entidade participa.

(min,max)SignificadoExemplo (aulas)
(0,1)opcional, no máximo umPassport
(1,1)obrigatório, exatamente umOrder → pertence a exatamente um Customer
(0,N)opcional, vários possíveisCustomer → pode fazer zero ou mais Orders

Dica. Lê sempre em voz baixa: “uma instância de A pode/tem de estar ligada a quantas de B?”. A resposta fala do outro lado da relação, mas escreve-se junto de A. Ex.: “Um leitor pode ter zero ou mais empréstimos” → LEITOR (0,N); “um empréstimo pertence a exatamente um leitor” → EMPRESTIMO (1,1). Escreve no exame que convenção usas (a resolução oficial usa a mesma: “do lado de EDITORA é 0..N, do lado de LIVRO é 1..1”).

1.4 Método para resolver um problema de ER

  1. Sublinha os substantivos relevantes → candidatas a entidades. Descarta os que são só atributos.
  2. Para cada entidade, lista os atributos do enunciado e escolhe o identificador (se o enunciado não dá um, cria um ID e diz que o criaste).
  3. Classifica atributos “especiais”: composto? multivalor? derivado?
  4. Sublinha os verbos → relacionamentos. Para cada um: quem participa? binário/ternário/recursivo?
  5. Cardinalidade máxima (1:1, 1:N, N:M) a partir de frases como “cada X tem um único Y” / “um X pode ter vários Y”.
  6. Participação mínima (0 ou 1) a partir de “tem de”, “pelo menos um”, “pode não ter”, “inclui um ou vários”.
  7. Atributos do relacionamento: qualquer dado que só faz sentido para um par concreto (ex.: estado de devolução de um livro num empréstimo).
  8. Verifica regra a regra: cada bullet do enunciado deve ter correspondência no teu diagrama.
Atenção. No ER não há chaves estrangeiras — as ligações são os losangos. As FK só aparecem no passo seguinte (modelo relacional). Pôr EditoraID dentro de LIVRO no ER é um erro frequente.

1.5 Exame modelo · Grupo I · Q1 — Modelo ER EXAME MODELO

Enunciado (resumo). Biblioteca municipal: livros, leitores, editoras, empréstimos.
  • Livro: ISBN, título, ano de publicação. Cada livro é publicado por uma única editora; uma editora pode publicar vários livros.
  • Editora: identificador, nome, país.
  • Leitor: nº de leitor, nome, e-mail, data de inscrição.
  • Empréstimo: um único leitor, data de levantamento, data prevista de devolução. Pode incluir vários livros; um livro pode estar em vários empréstimos ao longo do tempo. Para cada livro num empréstimo, regista-se o estado em que foi devolvido.

Porque é que EstadoDevolucao não fica em LIVRO nem em EMPRESTIMO? Em LIVRO teria um único valor por livro (mas o mesmo livro é devolvido em estados diferentes em empréstimos diferentes). Em EMPRESTIMO teria um único valor por empréstimo (mas um empréstimo tem vários livros). Só o par (empréstimo, livro) o determina → pertence ao relacionamento N:M.
Detalhes aceitáveis. A resolução diz que “outras respostas equivalentes e corretas devem ser aceites”. Por exemplo, EMPRESTIMO (1,N) vs (0,N) para “inclui livros” é discutível — o enunciado diz “um ou vários” (→ 1,N). Se tiveres dúvida, escreve a tua leitura do enunciado ao lado.

1.6 Modelo relacional

  • Relação = tabela: conjunto de tuplos (linhas, instâncias) com atributos (colunas) definidos; nº de atributos fixo; nome de atributo único; cada valor é atómico; a ordem dos tuplos não tem significado. Vocabulário: Tabela = relação · Linha = tuplo · Coluna = atributo.
  • Chave candidata: conjunto mínimo de atributos que identifica unicamente cada tuplo. Chave primária (PK): a candidata escolhida; valores únicos e nunca NULL. Chave estrangeira (FK): atributo(s) que referencia(m) a chave de outra relação — representa a ligação entre tabelas.

1.7 Exame modelo · Grupo I · Q2 — Esquema relacional EXAME MODELO

Aplica as regras tabela a tabela, na ordem: entidades fortes “do lado 1” primeiro, depois as do lado N, por fim as tabelas das N:M.

Elemento do ERResultado
EDITORAEDITORA(EditoraID, Nome, Pais)
LIVRO + 1:N com EDITORALIVRO(ISBN, Titulo, AnoPublicacao, EditoraID) — a PK de EDITORA (lado 1) vira FK em LIVRO (lado N)
LEITORLEITOR(NumeroLeitor, Nome, Email, DataInscricao)

Chaves estrangeiras (a pedir explicitamente).
  • LIVRO.EditoraID → EDITORA.EditoraID
  • EMPRESTIMO.NumeroLeitor → LEITOR.NumeroLeitor
  • EMPRESTIMO_LIVRO.EmprestimoID → EMPRESTIMO.EmprestimoID
  • EMPRESTIMO_LIVRO.ISBN → LIVRO.ISBN
Chave primária de EMPRESTIMO_LIVRO = (EmprestimoID, ISBN). Cada um dos dois atributos é simultaneamente parte da PK e FK.

Em SQL (caso peçam CREATE TABLE — variação provável)

CREATE TABLE EDITORA (
  EditoraID INTEGER PRIMARY KEY,
  Nome TEXT NOT NULL,
  Pais TEXT
);
CREATE TABLE LIVRO (
  ISBN TEXT PRIMARY KEY,
  Titulo TEXT NOT NULL,
  AnoPublicacao INTEGER,
  EditoraID INTEGER NOT NULL,
  FOREIGN KEY (EditoraID) REFERENCES EDITORA(EditoraID)
);
CREATE TABLE EMPRESTIMO_LIVRO (
  EmprestimoID INTEGER,
  ISBN TEXT,
  EstadoDevolucao TEXT,
  PRIMARY KEY (EmprestimoID, ISBN),
  FOREIGN KEY (EmprestimoID) REFERENCES EMPRESTIMO(EmprestimoID),
  FOREIGN KEY (ISBN) REFERENCES LIVRO(ISBN)
);

NOT NULL em LIVRO.EditoraID traduz o (1,1) (participação obrigatória). Se fosse (0,1), a FK poderia ser NULL.

Erros frequentes. (1) Esquecer a tabela da N:M ou pôr uma FK “de livros” dentro de EMPRESTIMO. (2) Esquecer EstadoDevolucao. (3) Pôr a FK no lado errado do 1:N (a FK vai sempre para o lado N). (4) PK simples em EMPRESTIMO_LIVRO (um empréstimo teria só um livro). (5) Não assinalar as FK.

1.8 Exame modelo · Grupo I · Q3 — Chaves e integridade de entidade EXAME MODELO

COLABORADOR(ColabID, Nome, Email, NIF, Departamento). Q3: indique duas possíveis chaves candidatas e dê um exemplo de violação da integridade de entidade.
  • Chaves candidatas: ColabID e NIF — identificam univocamente cada colaborador, são mínimas (1 atributo) e assume-se que não admitem NULL. (Email também serve se for único.)
  • Não são candidatas: Nome (há homónimos) e Departamento (repete-se). Um conjunto como {ColabID, Nome} é único mas não é mínimo (super-chave).
  • Porque é que só uma é “a” PK? A PK é a candidata escolhida (aqui ColabID); as restantes ficam como chaves alternativas (UNIQUE).
  • Violação da integridade de entidade: inserir um colaborador com ColabID = NULL (a PK não pode ser nula) ou inserir um ColabID já existente (PK duplicada).
Dica. Resposta completa em 3 linhas: definição de candidata (única + mínima) → duas candidatas com justificação → exemplo concreto INSERT … VALUES (NULL, 'Ana', …). Dar a definição não custa nada e mostra domínio.

1.9 Variações possíveis e exercícios

O que a professora pode mudar sem sair da matéria.
  • Outro domínio (hospital, escola, loja, transportes…), com outras regras de negócio.
  • Outros tipos de relacionamento: 1:1 (com participação opcional), recursivo, ternário.
  • Outros tipos de atributo: composto (morada), multivalor (telefones), derivado (idade).
  • Pedir o contrário: dado um esquema/diagrama, identificar chaves, FK, cardinalidades ou violações de integridade.
  • Pedir CREATE TABLE em vez de esquema abstrato; pedir justificação (“porquê tabela própria?”).
  • Pedir integridade referencial (em vez de entidade) ou domínio na pergunta de chaves.

Caso A — Clínica veterinária (composto + multivalor + derivado + 1:N + N:M com atributos)

Enunciado. Uma clínica guarda os donos (NIF, nome, morada = rua, cidade e código postal, e vários telefones) e os animais (nº de chip, nome, espécie, data de nascimento; a idade é consultada com frequência). Cada animal pertence a um único dono; um dono pode (ainda) não ter animais. Os veterinários têm cédula profissional e nome. Uma consulta é feita por um veterinário a um animal numa data/hora e tem um diagnóstico; um animal pode ter várias consultas e ser visto por vários veterinários. Faça o ER e o esquema relacional.
ER
  • DONO(NIF, Nome, Morada(Rua, Cidade, CodPostal), {Telefone})
  • ANIMAL(ChipID, Nome, Especie, DataNascimento, Idade derivado)
  • VETERINARIO(Cedula, Nome)
  • DONO–possui–ANIMAL: 1:N, DONO (0,N), ANIMAL (1,1)
  • ANIMAL–consulta–VETERINARIO: N:M, ambos (0,N); atributos DataHora, Diagnostico
Relacional
  • DONO(NIF, Nome, Rua, Cidade, CodPostal)
  • DONO_TELEFONE(NIF, Telefone) — FK NIF→DONO
  • ANIMAL(ChipID, Nome, Especie, DataNascimento, NIF) — FK NIF→DONO
  • VETERINARIO(Cedula, Nome)
  • CONSULTA(ChipID, Cedula, DataHora, Diagnostico) — FK ChipID→ANIMAL, Cedula→VETERINARIO
Porquê? Morada composta → 3 colunas. Telefones multivalor → tabela própria (cada valor atómico). Idade derivada → não se guarda. DataHora entra na PK de CONSULTA porque o mesmo animal pode ver o mesmo veterinário várias vezes; sem ela, só haveria uma consulta por par.

Caso B — Universidade (N:M com atributo, 1:1, recursivo)

Enunciado. Alunos (nº mecanográfico, nome) inscrevem-se em unidades curriculares (código, nome, ECTS); cada inscrição tem ano letivo e nota (pode ainda não existir). Cada UC é lecionada por um docente (ID, nome); um docente leciona várias UC. Cada UC tem exatamente um coordenador (docente) e um docente coordena, no máximo, uma UC. Cada docente pode ter um docente orientador.
ER
  • ALUNO(NumAluno, Nome) · UC(CodUC, Nome, ECTS) · DOCENTE(DocenteID, Nome)
  • ALUNO–inscreve-se–UC: N:M, atributos AnoLetivo, Nota; ALUNO (0,N), UC (0,N)
  • DOCENTE–leciona–UC: 1:N; DOCENTE (0,N), UC (1,1)
  • DOCENTE–coordena–UC: 1:1; DOCENTE (0,1), UC (1,1)
  • DOCENTE–orienta–DOCENTE: recursivo 1:N; orientador (0,N), orientado (0,1)
Relacional
  • ALUNO(NumAluno, Nome)
  • DOCENTE(DocenteID, Nome, OrientadorID) — FK→DOCENTE, pode ser NULL
  • UC(CodUC, Nome, ECTS, DocLecionaID, DocCoordID) — duas FK→DOCENTE; DocCoordID UNIQUE
  • INSCRICAO(NumAluno, CodUC, AnoLetivo, Nota)
Porquê? No 1:1 a FK vai para o lado de participação total (UC tem sempre coordenador) e fica UNIQUE, garantindo que um docente não coordena duas UC. AnoLetivo na PK permite repetir a UC noutro ano; se o enunciado dissesse “só uma inscrição por aluno e UC”, a PK seria (NumAluno, CodUC). Nota pode ser NULL.

Caso C — “Que violação é esta?” (integridade)

Dadas DEPARTAMENTO(DepID, Nome) com {(1,TI), (2,RH)} e FUNCIONARIO(FuncID, Nome, NIF, DepID) com {(10,Ana,111,1), (11,Rui,222,2)}, onde DepID → DEPARTAMENTO. Diz se cada operação viola alguma restrição:

OperaçãoResposta
a) INSERT INTO FUNCIONARIO VALUES (10,'Eva','333',1)Entidade: FuncID = 10 já existe (PK duplicada).
b) INSERT INTO FUNCIONARIO VALUES (12,'Eva','333',3)Referencial: não existe departamento 3.
c) INSERT INTO FUNCIONARIO VALUES (NULL,'Eva','333',1)Entidade: PK nula.
d) INSERT INTO FUNCIONARIO VALUES (13,'Eva','333',NULL)Nenhuma — uma FK pode ser NULL se a ligação for opcional (se DepID fosse NOT NULL, violava a regra de obrigatoriedade).
e) DELETE FROM DEPARTAMENTO WHERE DepID = 1Referencial: a Ana referencia o departamento 1. O SGBD rejeita (ou exige uma ação definida: CASCADE, SET NULL).
f) INSERT INTO FUNCIONARIO VALUES ('x','Eva','333',1) com FuncID INTEGERDomínio: valor de tipo errado.

Atenção. UPDATE e DELETE sem WHERE afetam todas as linhas. É a observação mais repetida nos slides: “always use a WHERE clause!”. Textos entre aspas simples; números sem aspas; lista de colunas e lista de valores na mesma ordem.

2.2 SELECT: a ordem das cláusulas

SELECT   [DISTINCT] colunas / expressões / agregações
FROM     tabela [AS alias]
[JOIN    outra_tabela [AS alias] ON condição_de_junção]
[WHERE   condição sobre linhas]
[GROUP BY colunas]
[HAVING  condição sobre grupos]
[ORDER BY colunas [ASC|DESC]]
[LIMIT   n];

Ordem em que o SGBD “pensa” (útil para perceber erros): FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Por isso o WHERE não pode usar funções de agregação (os grupos ainda não existem) e o HAVING sim.

2.3 JOIN: combinar tabelas

  • JOIN … ON (= INNER JOIN) liga linhas de duas tabelas quando a condição se verifica — normalmente FK = PK. Linhas sem correspondência desaparecem.
  • LEFT JOIN mantém todas as linhas da tabela da esquerda; onde não há correspondência, as colunas da direita vêm a NULL. Usa-se para “mesmo os que não têm…” e para anti-junções.
  • Aliases (FROM MANUTENCAO AS M) encurtam e resolvem ambiguidades: se duas tabelas têm a coluna TecnicoID, escreve M.TecnicoID.
  • Relações N:M precisam de passar pela tabela de associação (ex.: MANUTENCAO → MANUTENCAO_CATEGORIA → CATEGORIA): dois JOIN seguidos.
Como o slide decompõe uma consulta com JOIN + WHERE. FROM employees: começa na tabela principal → JOIN departments ON …: junta cada linha ao departamento correspondente → WHERE …: filtra a tabela “larga” resultante → SELECT …: escolhe as colunas finais.

2.4 Agregação: GROUP BY e HAVING

  • GROUP BY junta linhas com o mesmo valor em “linhas-resumo”. Regra: toda a coluna no SELECT que não seja agregada tem de estar no GROUP BY.

3 · Módulo 3Inteligência para Negócios: OLTP, OLAP, Data Warehouse, ETL e modelo dimensional

Peso no exame: 5 valores em 20. Matéria mais “de conceito”: vale a pena dominar as definições e ser capaz de desenhar um modelo dimensional simples.

3.1 Dos dados à decisão

  • Inteligência para Negócios (BI): métodos e tecnologias que transformam dados em informação útil para apoiar decisões — recolher e integrar, organizar e analisar, comunicar (relatórios, indicadores, painéis).
  • Cadeia: Dados (registos: data, loja, viagem) → Informação (nº de entregas por mês) → Conhecimento (que meses/centros têm mais volume) → Decisão (ajustar recursos). Os dados, por si só, não garantem uma boa decisão.
  • Começar pelas perguntas de negócio: “Quantas entregas por mês?”, “Que centros realizam mais entregas?”. Antes de analisar, define: a pergunta, os dados necessários e a medida que responde.
  • Processo de negócio = conjunto de atividades relacionadas que produz um resultado (preparar encomenda → organizar viagem → transportar → entregar). Cada atividade gera dados; estes ficam em sistemas diferentes, com formatos distintos, erros e duplicados → têm de ser integrados e preparados.
  • Big Data: dados cuja dimensão, rapidez de geração ou diversidade tornam o tratamento mais exigente — os 3 V: Volume, Velocidade, Variedade.
Da operação à decisão: onde entram OLTP, ETL, Data Warehouse e OLAP.

3.2 OLTP vs OLAP · Data Warehouse · ETL

OLTP (Online Transaction Processing)OLAP (Online Analytical Processing)
ObjetivoRegistar as operações diáriasAnalisar dados e apoiar decisões
OperaçõesInserir e atualizar registosAgregar e comparar dados
DadosSobretudo atuais e detalhadosIntegrados e históricos
ConsultasGeralmente curtas (muitas transações curtas)Analíticas, muitas vezes complexas

Em resumo (slide): OLTP regista o que acontece; OLAP ajuda a perceber o que aconteceu.

Porque não analisar diretamente no sistema operacional? As BD operacionais são feitas para registar/atualizar; uma análise histórica pode exigir muitos registos e juntar várias tabelas, pode não existir todo o histórico, e consultas demoradas prejudicam o desempenho das operações diárias.

  • Data Warehouse (DW): repositório que integra dados de diferentes fontes e os organiza para análise; conserva informação histórica; permite comparar períodos, locais e tipos de operação; facilita relatórios e indicadores.
  • ETL = Extração (recolher dos sistemas de origem), Transformação (validar, limpar, uniformizar), Carregamento (guardar no DW). Ex. de transformação: uniformizar formatos de data, corrigir códigos de loja inconsistentes, tratar duplicados.
  • Arquiteturas OLAP: ROLAP (tabelas relacionais e consultas SQL), MOLAP (estruturas multidimensionais, podendo pré-calcular agregações), HOLAP (combina as duas). Escolha depende do volume, do desempenho pretendido e da tecnologia.

3.3 O modelo dimensional

ConceitoDefiniçãoExemplo (entregas)
FactoO acontecimento que queremos analisarUma etapa de entrega / uma entrega
MedidaValor que queremos quantificarPeso transportado, volume, custo, nº de entregas
DimensãoPerspetiva/contexto de análise do facto; atributos descritivos que permitem filtrar e agruparData, loja, centro, camião
GranularidadeNível de detalhe de cada registo da tabela de factos“Uma etapa de entrega numa viagem” → cada linha é uma etapa

Granularidade primeiro. Define-a antes de escolher as medidas; tem de ser clara e consistente em toda a tabela. Uma definição incorreta leva à contagem duplicada de entregas, peso ou quilómetros. Cada linha da tabela de factos tem de corresponder ao evento definido.

Tabela de factos vs tabelas de dimensão

Tabela de factos: regista eventos ao nível da granularidade; contém medidas; inclui chaves estrangeiras para as dimensões (ex.: DataKey → DimData, LojaKey → DimLoja).
Tabelas de dimensão: descrevem o contexto do evento; contêm atributos descritivos; permitem filtrar e agrupar os factos. Cada dimensão tem a sua PK, referenciada pela FK da tabela de factos.

Tipos de medidas (aditividade)

TipoRegraExemplo
AditivaPode ser somada em todas as dimensõesPeso entregue (se cada encomenda for contabilizada uma só vez); nº de entregas; custo
Semi-aditivaSomável em algumas dimensões, não em todasQuilómetros acumulados de um camião ao longo do tempo (somas entre camiões ok; somar no tempo não)
Não aditivaNão se soma; recalcula-se a partir dos valores que lhe dão origem% de entregas pontuais, médias, rácios (custo por km)

A resolução do exame modelo repete a ideia: “uma média ou uma percentagem não é, em geral, aditiva: deve ser recalculada a partir dos valores que lhe dão origem”. Uma medida só é fiável se estiver definida de forma consistente com a granularidade.

Galaxy: p.ex. analisar “entregas” e “custos de transporte” em duas tabelas de factos que partilham as dimensões Data, Centro e Camião.

V4 — Outro contexto: manutenção de bicicletas (liga o Grupo III ao Grupo II)

Enunciado. A empresa de aluguer de bicicletas quer analisar os custos de manutenção por ano, técnico, especialidade, categoria de serviço e tipo de intervenção. Proponha um modelo dimensional.
  • Processo: intervenções de manutenção. Grão: uma intervenção de manutenção (uma linha por ManutencaoID).
  • Medidas: Custo (aditiva), NumIntervencoes (=1, aditiva). Custo médio = SUM(Custo)/SUM(NumIntervencoes) (não aditiva, recalcular).
  • Dimensões: DIM_TEMPO (ano; se houver data: mês, trimestre) · DIM_TECNICO (nome, certificação, anos de experiência, especialidade) · DIM_TIPO (corretiva/preventiva) · DIM_CATEGORIA (nome da categoria).
  • Atenção ao grão! Uma intervenção pode ter várias categorias (tabela N:M no relacional). Se a tabela de factos tiver uma linha por intervenção e por categoria, o custo conta-se duas vezes para quem tem duas categorias — viola a ideia “cada linha = o evento definido”. Soluções: (a) grão “intervenção × categoria” e não somar o custo por intervenção em análises sem categoria; (b) tabela de bridge; (c) categoria principal. O ponto a mostrar no exame é perceber o risco da dupla contagem.

O mesmo exemplo em snowflake: DIM_TECNICO → DIM_ESPECIALIDADE (a especialidade passa para a sua própria tabela, ligada por FK).

5.1 O que pôr na folha A4 (frente e verso, manuscrita)

Frente — Módulo 1 + relacional

  • Notação ER: entidade, atributo, identificador (sublinhado), multivalor (oval dupla), composto, derivado (tracejado), relacionamento, (min,max).
  • Como ler (min,max): “uma instância de A tem quantas de B?” → escreve junto de A.
  • Tabela ER → relacional: 1:1, 1:N (FK no lado N), N:M (nova tabela, PK composta), recursivo, multivalor (tabela), composto (colunas), derivado (não se guarda), ternário.

  • Exemplo mínimo EMPRESTIMO_LIVRO(EmprestimoID, ISBN, Estado).

Verso — SQL + Módulo 3

  • Molde do SELECT com a ordem das cláusulas; ordem lógica (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT).
  • INSERT / UPDATE (SET…WHERE) / DELETE; WHERE sempre.
  • JOIN … ON; LEFT JOIN … IS NULL; NOT EXISTS (modelo); IN (subconsulta); NOT IN + NULL.
  • WHERE vs HAVING; COUNT(*) vs COUNT(col); regra do GROUP BY.
  • BETWEEN (inclusivo), IN, LIKE (% e _), IS NULL.
  • OLTP vs OLAP (tabela), DW, ETL (E-T-L), 3 V, ROLAP/MOLAP/HOLAP.
  • Grão → dimensões → medidas; aditiva / semi / não aditiva; star / snowflake / galaxy.
  • Roll-up / drill-down / slice / dice / pivot (com 1 exemplo cada).

CREATE TABLE TECNICO (
  TecnicoID TEXT PRIMARY KEY,
  Nome TEXT NOT NULL,
  Certificacao TEXT,
  AnosExperiencia INTEGER,
  Especialidade TEXT
);
CREATE TABLE MANUTENCAO (
  ManutencaoID INTEGER PRIMARY KEY,
  Descricao TEXT,
  TecnicoID TEXT,
  Ano INTEGER,
  Tipo TEXT,
  Custo REAL,
  FOREIGN KEY (TecnicoID) REFERENCES TECNICO(TecnicoID)
);
CREATE TABLE CATEGORIA (
  CategoriaID INTEGER PRIMARY KEY,
  NomeCategoria TEXT NOT NULL
);
CREATE TABLE MANUTENCAO_CATEGORIA (
  ManutencaoID INTEGER,
  CategoriaID INTEGER,
  PRIMARY KEY (ManutencaoID, CategoriaID),
  FOREIGN KEY (ManutencaoID) REFERENCES MANUTENCAO(ManutencaoID),
  FOREIGN KEY (CategoriaID) REFERENCES CATEGORIA(CategoriaID)
);
